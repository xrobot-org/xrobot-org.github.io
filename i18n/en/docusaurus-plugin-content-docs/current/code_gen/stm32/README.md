# STM32 Code Generation

The `libxr stm32 setup` command of the code generator (the pip package `libxr`) sets up an STM32CubeMX project for LibXR: it parses the `.ioc` file, generates the C++ initialization code and integrates LibXR into the CMake build.

---

## Quick Start

In the root directory of the STM32CubeMX project, run:

```bash
libxr stm32 setup -d .
```

With the [`XRobot.xrobot`](https://marketplace.visualstudio.com/items?itemName=XRobot.xrobot) extension in VS Code, the configuration can also be edited on the GUI page of the extension, which runs the generation command after each change.

The command performs these steps in order:

1. Adds the LibXR submodule `Middlewares/Third_Party/LibXR` and writes `.gitmodules` (running `git init` first when the project is not a Git repository yet); an existing checkout is kept, and `--commit` switches it to a given commit;
2. Creates or completes `.gitignore` and `.gitattributes`;
3. Locates the `.ioc` file and parses it into `.config.yaml`;
4. Generates `app_main.cpp`, `app_main.h`, `flash_map.hpp` and `libxr_config.yaml` in `User/`;
5. Generates `cmake/LibXR.CMake` and includes it from `CMakeLists.txt`.

When the directory holds only the `.ioc` file and no code generated by STM32CubeMX yet, run `libxr stm32 cubemx-gen` first: it runs STM32CubeMX in script mode to generate the project from the `.ioc` file; then run `libxr stm32 setup`. The dialogs STM32CubeMX shows are answered as the options say: when the project was saved by another STM32CubeMX version, `--firmware keep` keeps its firmware package (Continue) and `--firmware migrate` migrates the project; `--download` lets STM32CubeMX download a missing firmware package and accept its license. A dialog without a matching option stops the run and reports its content. On Linux dialogs are not answered, and any dialog stops the run.

## Output Structure

After execution, the project directory contains the following generated or modified files:

```txt
.
├── .config.yaml                      # Parsed configuration from .ioc
├── .gitignore
├── .gitattributes
├── .gitmodules
├── User/
│   ├── app_main.cpp                  # Entry source
│   ├── app_main.h                    # Header of the entry source
│   ├── libxr_config.yaml             # LibXR runtime configuration
│   └── flash_map.hpp                 # Flash address mapping table
├── cmake/LibXR.CMake                 # CMake build config for LibXR
├── CMakeLists.txt                    # Modified to include LibXR
└── Middlewares/Third_Party/LibXR     # LibXR as a Git submodule
```

## app_main.cpp

The `app_main.cpp` file contains the LibXR initialization function `app_main()`.

Code between `/* User Code Begin N */` and `/* User Code End N */` is kept when the file is regenerated; everything else is regenerated every time.

Generated peripheral objects are `static` objects and stay valid after `app_main()` returns; local objects in User Code without `static` are destroyed when `app_main()` returns, so objects used for the lifetime of the program are declared `static`. Peripheral objects can be passed to threads or tasks as base class pointers; [Integrate with XRobot](../xrobot_inter.md) in this chapter describes a more complete approach.

An excerpt of the `app_main.cpp` generated for an STM32F407 project (without `--xrobot`); omitted lines are marked `// ...`:

```cpp
// Generated by `libxr gen` from DevC.ioc and User/libxr_config.yaml.
// Edit only between "User Code Begin" and "User Code End"; the rest is regenerated.
#include "app_main.h"

#include "cdc_uart.hpp"
#include "libxr.hpp"
#include "main.h"
#include "stm32_adc.hpp"
#include "stm32_can.hpp"
// ...

using namespace LibXR;

/* User Code Begin 1 */
/* User Code End 1 */

extern ADC_HandleTypeDef hadc1;
extern ADC_HandleTypeDef hadc3;
extern CAN_HandleTypeDef hcan1;
// ...

// DMA buffers (STM32F407IG: no D-cache)
alignas(4) static uint16_t adc1_buf[32];
alignas(4) static uint16_t adc3_buf[16];
// ...
alignas(4) static uint8_t spi1_rx_buf[32];
alignas(4) static uint8_t spi1_tx_buf[32];
// ...

extern "C" void app_main(void)
{
  /* User Code Begin 2 */
  /* User Code End 2 */

  // Timebase and platform
  static STM32TimerTimebase timebase(&htim2);
  PlatformInit(static_cast<uint32_t>(Thread::Priority::MEDIUM), 1024);
  static STM32PowerManager power_manager;

  // GPIO
  static STM32GPIO USER_KEY(USER_KEY_GPIO_Port, USER_KEY_Pin, EXTI0_IRQn);
  static STM32GPIO ACCL_CS(ACCL_CS_GPIO_Port, ACCL_CS_Pin);
  // ...

  // ADC
  // ...
  static STM32ADC adc3(&hadc3, adc3_buf, {ADC_CHANNEL_8}, 3.3);
  static auto& adc3_adc_channel_8 = adc3.GetChannel(0);
  UNUSED(adc3_adc_channel_8);

  // ...

  // PWM
  static STM32PWM pwm_tim1_ch1(&htim1, TIM_CHANNEL_1, false);
  // ...

  // SPI, UART, I2C, CAN
  static STM32SPI spi1(&hspi1, spi1_rx_buf, spi1_tx_buf, 3);
  static STM32UART usart1(&huart1, usart1_rx_buf, usart1_tx_buf, 5);
  // ...
  static STM32I2C i2c1(&hi2c1, i2c1_buf, 3);
  // ...
  static STM32CAN can1(&hcan1, 5);
  // ...

  /* User Code Begin 3 */
  while (true)
  {
    Thread::Sleep(UINT32_MAX);
  }
  /* User Code End 3 */
}
```

Peripheral objects are `static` objects. DMA buffers take one of two forms: aligned to the cache line on chips with a data cache (see [Cache](./cache.md)), and arrays aligned to 4 bytes on the others.

## How to Use

Call `app_main()` from the entry of the project:

### Bare-metal Project

```cpp
#include "app_main.h"

int main() {
    HAL_Init();
    SystemClock_Config();
    ...
    app_main();  // Initialize peripherals and start application
    while (1) {
        ...
    }
}
```

### FreeRTOS Project

Call `app_main()` in the default task `StartDefaultTask`. `app_main()` runs on the stack of the default task, whose stack depth is set in STM32CubeMX and has to hold it.

`CMSIS_V2` is the recommended FreeRTOS interface. Firmware packages such as STM32Cube FW_H7 V1.13.0 have removed the CMSIS-RTOS V1 wrapper, so projects on such a package can only use `CMSIS_V2`. When a project with the `CMSIS_V1` interface moves to such a package, STM32CubeMX removes FreeRTOS entirely, without a message. Open such a project with Continue to keep its firmware package, switch the interface to `CMSIS_V2`, then migrate.

With `CMSIS_V2`, STM32CubeMX always enables FreeRTOS software timers (`configUSE_TIMERS`), which adds a timer task. LibXR runs its timed tasks (`LibXR::Timer`) in its own thread, whose priority and stack depth `PlatformInit()` sets; when `configUSE_TIMERS` is on, LibXR warns at compile time. Overriding the following definitions in the `USER CODE BEGIN Defines` section of `Core/Inc/FreeRTOSConfig.h` turns off the software timers, together with the CMSIS-RTOS2 `osTimer` API and event flags set from interrupts, which depend on them; `INCLUDE_xTimerPendFunctionCall` stays off. A project with `INCLUDE_xTimerPendFunctionCall` disabled in STM32CubeMX requires this override; without it, `freertos_os2.h` stops the build with `#error "Definition INCLUDE_xTimerPendFunctionCall must equal 1 to implement Event Flags API."`. That section is kept when code is regenerated.

```c
/* USER CODE BEGIN Defines */
#undef configUSE_TIMERS
#define configUSE_TIMERS 0
#undef configUSE_OS2_TIMER
#define configUSE_OS2_TIMER 0
#undef configUSE_OS2_EVENTFLAGS_FROM_ISR
#define configUSE_OS2_EVENTFLAGS_FROM_ISR 0
/* USER CODE END Defines */
```

## Optional Arguments

| Argument   | Description                             |
| ---------- | --------------------------------------- |
| `-d`       | Specify STM32 project root directory (default: current directory) |
| `-t`       | Set the terminal device (such as `usart1` or `usb_fs_cdc`), stored as `terminal_source` in `User/libxr_config.yaml` |
| `--xrobot` / `--no-xrobot` | Emit `XR_REGISTER` registrations and `XROBOT_MAIN();`, or not, see [Integrate with XRobot](../xrobot_inter.md); without either the project keeps its choice |
| `--commit` | Check out the LibXR submodule at this commit; without it the existing checkout is kept, and a new submodule starts at the commit this libxr release pins |
| `--git-source` | The Git source a missing LibXR is cloned from: `auto` (default), `github`, a base URL, a repository URL or a local repository; `.gitmodules` always records the GitHub URL |
| `--git-mirrors` | Comma-separated mirror base or repository URLs, tried with `--git-source auto`; the environment variable `XR_GIT_MIRRORS` takes the same form |
| `--verbose` | Enable debug logging |

## Toolchain Switch

To switch between GCC and Clang or change the Clang standard library, use:

```bash
libxr stm32 toolchain gcc
libxr stm32 toolchain clang -g
libxr stm32 toolchain clang --newlib
libxr stm32 toolchain clang --picolibc
```

The command edits `CMakePresets.json` and `cmake/starm-clang.cmake`. Switching between gcc and clang removes the `build/` and `cmake-build*` directories: CMake does not change the compiler of an existing build directory, so the next build configures a new one. `clang` without a standard library option keeps the current one.

`-g` (hybrid) compiles with ST Arm Clang and links with the GNU toolchain. `cmake/starm-clang.cmake` finds the GNU toolchain from the environment variables `CLANG_GCC_CMSIS_COMPILER` (the ST Arm Clang installation directory, holding `multilib.gnu_tools_for_stm32.yaml`) and `GCC_TOOLCHAIN_ROOT` (the `bin` directory of `arm-none-eabi-gcc`), so both must be set before building.

## Project Requirements

- Must be a CMake project exported from STM32CubeMX  
- Must contain a valid `.ioc` file  
- Must enable Mutex when using FreeRTOS(`configUSE_MUTEXES`)  
- Peripherals use the HAL driver, with Generate Code left on in the Project Manager  
- The HAL timebase uses a general-purpose timer at the highest interrupt priority, see [Time Base](./timebase.md)

---

## Build Optimization

In the settings block at the top of `cmake/LibXR.CMake`, `LIBXR_OPT_DEBUG` (default `-Og`) is the Debug optimization level of the application target, including the sources in `User/`; in Debug builds the LibXR library `xr` (which also compiles the sources of XRobot Modules) and the libraries CubeMX generates (HAL, FreeRTOS and so on) use `-O2`. `LIBXR_OPT_RELEASE` is the Release level of the application, `xr` and these libraries; `""` keeps the level of the toolchain file (`-Os` for GCC and `-Oz` for ST Arm Clang as CubeMX writes them).

## Related Commands

| Command                  | Description                                    |
| ------------------------ | ---------------------------------------------- |
| `libxr stm32 cubemx-gen` | Run STM32CubeMX script-mode generation only    |
| `libxr parse`            | Parses `.ioc` and writes `.config.yaml`        |
| `libxr gen`              | Generates the entry source, `app_main.h` and `flash_map.hpp` from the YAML written by `libxr parse`, and updates `libxr_config.yaml` |
| `libxr stm32 flash-info` | Prints the internal flash layout of an STM32 model as YAML |
| `libxr stm32 cmake`      | Integrates LibXR into the project build system |
| `libxr stm32 toolchain`  | Switch toolchain and standard library          |

The `xr_*` commands of libxr before 6.0.0 (such as `xr_cubemx_cfg`) still work with their arguments and meanings unchanged: they name their new command when they run and are removed in 7.0.0. The [CodeGenerator README](https://github.com/xrobot-org/LibXR_CppCodeGenerator#旧命令--old-commands) lists them.
